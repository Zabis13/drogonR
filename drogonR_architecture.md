# drogonR — Architecture & Requirements

## Overview

R package wrapping Drogon C++ HTTP framework as a high-performance replacement for plumber.
Drogon runs in a dedicated C++ thread; R handlers execute in the main R thread via a thread-safe queue.

## Threading Model

```
[Drogon I/O threads]  →  [Lock-free Request Queue]  →  [R Main Thread]
        ↑                                                      ↓
  Accept HTTP                                         Execute R handler
  Parse JSON                                          Build R response
  TLS / HTTP2                                               ↓
        ←──────────────── [Response Callback] ←────────────────
```

**Rules:**
- All R calls (`SEXP`, `Rf_eval`, etc.) → main thread only
- Drogon I/O threads never touch R objects
- Queue is bounded (backpressure when R is saturated)
- C++-only routes bypass the queue entirely

## Core Components

### 1. Request Queue (`request_queue.cpp`)
- `moodycamel::ConcurrentQueue` (header-only, bundled)
- Drogon pushes `DrogonRequest` structs
- R event loop polls via `later::later()` or busy-wait with `R_CheckUserInterrupt()`
- Backpressure: return HTTP 503 when queue > N

### 2. R Dispatcher (`r_dispatcher.cpp`)
- Runs on main R thread
- Dequeues requests, calls R closure, enqueues response
- Protects SEXP objects with `Rf_protect/Rf_unprotect`
- Catches R errors → HTTP 500 with message

### 3. Server Lifecycle (`drogon_server.cpp`)
- `drogon_start(port, threads, queue_size)` — C entry point
- Drogon runs in `std::thread`, detached from R
- `drogon_stop()` — graceful shutdown with drain

### 4. R Bridge (`r_bridge.h`)
- Pure C API (no C++ exceptions cross the boundary)
- Structs for serialized request/response (raw bytes, no SEXP)
- Ownership: C++ owns memory until handed to R dispatcher

## R API (User-Facing)

```r
library(drogonR)

# Register routes
dr_get("/health", function(req) {
  dr_response(200, list(status = "ok"))
})

dr_post("/predict", function(req) {
  data <- req$body$data
  result <- model_predict(data)
  dr_response(200, list(prediction = result))
})

# C++-only route (no R involvement)
dr_get_cpp("/metrics", "prometheus_handler")

# Start server
dr_serve(port = 8080, threads = 4, workers = 8)
```

- C++17 compiler (GCC ≥ 7, Clang ≥ 5, MSVC 2019+)

## Worker Model (Multi-R-Process)

```
dr_serve(port = 8080, workers = 8)
```

- drogonR forks N R processes (like `parallel::mclapply`)
- Each worker has own R session + Drogon listener on same port (SO_REUSEPORT)
- No shared R state between workers
- Session objects (models, data) loaded per-worker at startup via `on_worker_start`

```r
dr_serve(
  port = 8080,
  workers = 8,
  on_worker_start = function() {
    model <<- load_model("mnist.gguf")
  }
)
```

## Middleware Chain

```
Request → [Auth MW] → [Rate Limit MW] → [CORS MW] → [R Handler] → Response
              ↓ (C++ layer, before R)                    ↓ (R layer)
```

Auth, rate limiting, CORS — implemented in C++ middleware, never reach R.
